# Cortex v2.0.2

Cortex v2.0.2 is a patch release. It keeps everything v2.0.0 and v2.0.1
introduced. It updates Next.js and installs fewer packages; the supported Node
range, browser sign-in, the MCP tool roster and the database upgrade boundary are
the same as in v2.0.1.

Compatibility: Node `>=22.18.0 <23` (the release workflow uses 22.23.2); the
optional wizard needs Vercel CLI 50.5.1 or newer.

## What changed

- **Next.js security update.** Next.js moves from 16.3.4 to 16.3.8. Versions
  16.2.0 up to, but not including, 16.3.6 are affected by
  [GHSA-vcvr-r3jv-pc5j](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j), a
  critical remote code execution advisory in the Node.js `ImageResponse` from
  `next/og`. An application is affected when it passes attacker-controlled
  values into the SVG content, attributes or styles of a generated image. Cortex
  does not import `next/og`, and its icons are static image files, so no Cortex
  route generates an image this way and v2.0.1 deployments do not run the
  affected code. This release updates anyway, so that no published Cortex
  release pins a version in the affected range. No advisory in GitHub's
  advisory database affected 16.3.8 when this release was prepared. Only
  Next.js and its own `@next/env` and `@next/swc-*` packages change version.
- **Smaller install.** `@modelcontextprotocol/sdk` is no longer a dependency.
  Cortex used it for one type, which now comes from
  `@modelcontextprotocol/server`, the package the MCP route already runs on.
  That package, already installed as a required peer of `mcp-handler`, is now
  declared directly at the same version, 2.0.0. The lockfile lists 82 fewer
  packages (397 instead of 479), all of them production dependencies of the
  removed SDK, including express, express-rate-limit, hono, cors and
  ip-address. No remaining package changed version in that change, and the
  unused `hono` override is removed. The MCP tools and their behavior are
  unchanged.
- **For contributors.** The optional SonarQube job in the Build workflow now
  skips, instead of failing, on runs that Dependabot starts. GitHub gives those
  runs no Actions secrets, so the job's configuration check failed on every
  Dependabot pull request. Every other run is analyzed as before, and a test
  checks the job's condition.

## Action required

- **From v2.0.1:** nothing. Redeploy to run Next.js 16.3.8.
- **From v2.0.0:** the timezone change from
  [v2.0.1](v2.0.1.md#action-required) applies. If `BRAIN_TZ` is unset or empty,
  daily log boundaries use UTC. Before redeploying, set `BRAIN_TZ` to the IANA
  timezone your daily logs should follow. Nothing else is required.
- **From v1.2.0 or earlier:** follow the
  [v2.0.0 upgrade requirements](v2.0.0.md#action-required-for-existing-installations)
  first. They still apply in full, including the administrator-reviewed plan for
  existing v1.2.0 databases. The `BRAIN_TZ` change above applies too.

`npm run update` is an interactive source/deployment helper, not a database upgrade
tool. It follows current `main`, which may advance beyond this snapshot. Installing
an exact release instead requires selecting that tag or archive explicitly.

## Linux and macOS setup

The [v2.0.2 release](https://github.com/Obelyth/cortex/releases/tag/v2.0.2) contains
`cortex-v2.0.2.tar.gz`. Download it, then extract it:

```bash
tar -xzf cortex-v2.0.2.tar.gz
cd cortex-v2.0.2
```

On Linux, run `bash "Cortex Setup.sh"`. On macOS, open **Cortex Setup.command**
from the extracted folder. Prerequisites and launcher behavior are unchanged from
v2.0.0; the [v2.0.0 setup section](v2.0.0.md#linux-and-macos-setup) describes them.

## Package and verification

The source archive is built from the release tag after the portable checks,
production build and zero-skip native integration gates pass at that tag, and it
is published only after a maintainer approves the release. With an authenticated
GitHub CLI, verify the downloaded file:

```bash
gh attestation verify cortex-v2.0.2.tar.gz --repo Obelyth/cortex
```

An attestation identifies the source/workflow that produced an artifact; it is not
a claim that every configured provider works in your deployment. Tagged snapshots
do not receive backported fixes; see the [security policy](../../SECURITY.md).
