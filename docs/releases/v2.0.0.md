# Cortex v2.0.0

Cortex v2.0.0 brings the five-tab Ink and Paper dashboard to a blank, self-hosted
installation. It includes Linux and macOS setup entry points in one source
archive. You supply your accounts, private notes repository and access credentials;
this is not a managed-hosting subscription or a native desktop application.

This is a major release because the supported Node version, browser sign-in
requirements and database upgrade boundary have changed since v1.2.0. Read the
action requirements before updating an existing deployment.

## What changed

- **Dashboard:** Ops, Overview, Ask, Trends and Settings share dim Paper and dark
  Ink themes, rounded surfaces, subtle dot textures and responsive layouts. Button
  swipes are decorative and never delay clicks. An optional orange-and-teal cursor
  outline turns slowly while leaving the native pointer visible; touch and reduced
  motion keep it off.
- **Working context:** Overview holds editable working notes and project-context
  previews. Selection starts at None. Previewing or clearing a project does not
  write notes, queue a job or invoke a reader model. Ask links to this same workflow.
- **Operations:** readiness and receipts distinguish configuration presence from
  verified authority and actual outcomes. Supported checks, migration commands and
  deployments require separate grants and explicit confirmation.
- **Fresh installation:** the brain template has only an empty profile and index.
  A new, dedicated database can use the reviewed pristine bootstrap bundle. No
  personal notes, sample projects, credentials or historical receipts are included.
- **Client access:** trusted MCP clients have eleven tools, including project
  handoff. Guests retain scoped ask and propose access, without direct note writes.
  Citation checks prove quoted text appears in a source, not that it is true.

The public release does not include private context-package editors, autonomous
lifecycle controls, or an unlimited-memory guarantee. Supported behavior and the
exact tool roster are documented in the [README](../../README.md).

## Action required for existing installations

1. **Back up first.** Preserve the private notes repository and database separately.
   Working notes, device records and operations history are not recoverable from
   the Markdown repository alone. Record the source revision and provider settings
   needed for recovery; do not publish those credentials in an issue.
2. **Use Node 22.** Local setup and builds require `>=22.18.0 <23`; the release
   workflow uses 22.23.2. Node 20, earlier Node 22 releases, and newer major versions
   are outside this release's supported range. Check the hosting project's Node
   setting as well as your local runtime.
3. **Configure browser access.** Set a distinct `CONSOLE_PASSCODE` in the running
   deployment's environment before deployment. Keep it separate from
   `CONNECTOR_PATH_SECRET` and `MCP_TOKEN`. Visit the protected console path and
   unlock the browser. This passcode is not an MCP credential or Google login.
4. **Check database compatibility before deploying.** Existing v1.2.0 databases
   predate the supported Ops migration baseline. This release does not provide an
   automatic upgrade for them. Preserve that database and obtain an
   administrator-reviewed integration plan before deploying the new source against
   it. Do not run pristine bootstrap or manufacture migration ledger entries.
5. **For an already-supported database, review forward migrations.** The current
   apply runner requires the Ops ledger and agent-unit migrations already recorded
   and a compatible schema. A read-only check can list pending files without proving
   an apply is supported. Follow the [database guide](../database-bootstrap.md),
   review the target and plan, then explicitly approve only supported forward work.
   Historical rows without checksums are a separate blocker: dashboard apply needs
   evidence-backed administrator reconciliation, not invented hashes of today's
   files. See [missing historical checksums](../database-bootstrap.md#historical-rows-without-checksums).
6. **Configure only the services you intend to use.** Dashboard operations need
   application-source settings, dedicated provider grants and receipt storage.
   Basic note browsing does not need these grants or a paid reader key. See
   [optional services](../../README.md#add-services-when-you-need-them).

`npm run update` is an interactive source/deployment helper, not a database upgrade
tool. It follows current `main`, which may advance beyond this snapshot. Installing
an exact release instead requires selecting that tag or archive explicitly.

## Linux and macOS setup

The [v2.0.0 release](https://github.com/Obelyth/cortex/releases/tag/v2.0.0) contains
`cortex-v2.0.0.tar.gz`. Download it, then extract it:

```bash
tar -xzf cortex-v2.0.0.tar.gz
cd cortex-v2.0.0
```

On Linux:

```bash
bash "Cortex Setup.sh"
```

The Linux launcher checks the OS, Node, npm, Git, GitHub CLI and Vercel CLI before
starting. Install Node 22.18 or newer within 22.x, Git, `gh`, and Vercel CLI 50.5.1
or newer using tools you trust. Then rerun the launcher. It does not invoke `sudo`,
pick a Linux package manager, or change your global Node configuration. File-manager
double-click behavior varies by desktop; the command above is the supported entry
point. Browser-based setup remains available without local tools.

On macOS, open **Cortex Setup.command** from the extracted folder. The launcher
checks prerequisites and asks before installing missing tools. If it selects the
versioned Homebrew Node 22 runtime, that selection is local to the setup process,
not a replacement for your global Node configuration.

Both paths use the same interactive onboarding wizard. Install/sign-in steps are
not proof that a deployment, database, model or mail service works. The wizard
separately asks before provider configuration and deployment. Credential entry can
be visible in the terminal; use a private session and do not share its transcript.

With all prerequisites already installed and both provider CLIs signed in, the
manual alternative on either system is:

```bash
npm ci --ignore-scripts
npm run onboard
```

Follow the [fresh-install guide](../../README.md#start-with-a-private-blank-brain)
for browser setup, private repository creation, exact environment fields and
optional services. A new database and an existing database have different paths.

## Package and verification

The source archive is built from the release tag after the portable checks,
production build and zero-skip native integration gates pass at that tag. It is
not assembled from a developer's working directory. Local environment files,
installed dependencies, build output and private notes are not part of the package.

The workflow publishes a provenance attestation for the archive. With an
authenticated GitHub CLI, verify the downloaded file:

```bash
gh attestation verify cortex-v2.0.0.tar.gz --repo Obelyth/cortex
```

An attestation identifies the source/workflow that produced an artifact; it is not
a claim that every configured provider works in your deployment. Check Settings,
Ops and the relevant receipts after installation. Tagged snapshots do not receive
backported fixes; see the [security policy](../../SECURITY.md).
