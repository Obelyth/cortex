# Cortex v2.0.1

Cortex v2.0.1 is a patch release. It keeps everything v2.0.0 introduced. Apart
from the Overview layout and the `BRAIN_TZ` default (see Action required), it
changes nothing about how an installation runs: the supported Node range, browser
sign-in, the MCP tool roster and the database upgrade boundary are the same as in
v2.0.0.

Compatibility: Node `>=22.18.0 <23` (the release workflow uses 22.23.2); the
optional wizard needs Vercel CLI 50.5.1 or newer.

## What changed

- **Privacy.** Documentation examples and MCP tool descriptions now use neutral
  placeholder names, hosts, values and wording, and test fixtures and code
  comments were rewritten as self-contained examples.
- **Security updates.** The lockfile moves brace-expansion, fast-uri and
  ip-address to their patched releases, which resolves six Dependabot
  advisories. None of the three runs in the deployed server.
- **Documentation fixes.** The security policy describes what the health check
  actually probes, the environment example documents the timezone default and a
  missing setting, the maintenance template lists every trusted tool, and broken
  links in the setup and repository guides now point at their public sources.
- **Release publishing.** Publishing now waits for a maintainer's approval in the
  `release` environment after the checks at the tag pass. Only the release
  workflow publishes a release, and it stops before the checks run, and before
  anyone is asked to approve, when the tag is not on the default branch or does
  not match the package version or this version's release notes. The
  pull-request housekeeping workflow added since v2.0.0 does not run on version
  tags, and a test checks that no other workflow file in this repository reacts
  to a tag push or calls a release command.
- **Overview layout.** The Overview introduction and the working-notes workspace
  are shown as separate sections in both themes. Controls and their meanings are
  unchanged.
- **For contributors.** A GitHub Codespaces setup (Node 22, non-root, locked
  install) that does not start the server, run migrations or deploy; a
  documentation hub, a repository settings guide and an updated design
  reference; an optional Claude pull-request review workflow and housekeeping
  checks; documented export privacy checks; and evaluation scripts that take
  their label file from `--labels`.

## Action required

- **From v2.0.0:** if `BRAIN_TZ` is unset or empty, daily log boundaries now use
  UTC. Before redeploying, set `BRAIN_TZ` to the IANA timezone your daily logs
  should follow. Nothing else is required.
- **From v1.2.0 or earlier:** follow the
  [v2.0.0 upgrade requirements](v2.0.0.md#action-required-for-existing-installations)
  first. They still apply in full, including the administrator-reviewed plan for
  existing v1.2.0 databases. The `BRAIN_TZ` change above applies too.

`npm run update` is an interactive source/deployment helper, not a database upgrade
tool. It follows current `main`, which may advance beyond this snapshot. Installing
an exact release instead requires selecting that tag or archive explicitly.

## Linux and macOS setup

The [v2.0.1 release](https://github.com/Obelyth/cortex/releases/tag/v2.0.1) contains
`cortex-v2.0.1.tar.gz`. Download it, then extract it:

```bash
tar -xzf cortex-v2.0.1.tar.gz
cd cortex-v2.0.1
```

On Linux, run `bash "Cortex Setup.sh"`. On macOS, open **Cortex Setup.command**
from the extracted folder. Prerequisites and launcher behavior are unchanged from
v2.0.0; the [v2.0.0 setup section](v2.0.0.md#linux-and-macos-setup) describes them.

## Package and verification

The source archive is built from the release tag after the portable checks,
production build and zero-skip native integration gates pass at that tag, and it
is published only after a maintainer approves the release. With an authenticated
GitHub CLI, verify the downloaded file:

```bash
gh attestation verify cortex-v2.0.1.tar.gz --repo Obelyth/cortex
```

An attestation identifies the source/workflow that produced an artifact; it is not
a claim that every configured provider works in your deployment. Tagged snapshots
do not receive backported fixes; see the [security policy](../../SECURITY.md).
